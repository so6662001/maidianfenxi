# 错误码字典

## 一、错误码规范

```
6 位数字：前 2 位服务码 + 后 4 位业务码

服务码：
  00xxxx - 通用（跨服务）
  10xxxx - gateway
  11xxxx - auth
  12xxxx - meta / metric
  13xxxx - segment
  14xxxx - tag
  15xxxx - reach
  16xxxx - experiment
  17xxxx - report
  18xxxx - assistant
  19xxxx - decision / insight
  20xxxx - openapi
  21xxxx - admin / job
  22xxxx - collector

业务码分组：
  0001-0999 - 业务异常
  1000-1999 - 校验失败
  2000-2999 - 资源相关
  3000-3999 - 权限相关
  4000-4999 - 限流/熔断
  5000-5999 - 第三方调用
  9000-9999 - 系统内部
```

## 十七、使用规范

### 客户端错误响应

```json
{
  "code": 120002,
  "message": "指标查询超时",
  "data": null,
  "traceId": "abc123",
  "requestId": "req-xxx",
  "detail": "查询超过 30 秒，已自动 Kill"
}
```

### 错误响应原则

- `code = 0` → 成功
- `code != 0` → 失败
- HTTP 状态码与业务码语义一致
- `message` 用户可见，**禁止透传内部堆栈**
- `detail` 选填，开发环境显示
- `traceId` 必填，用于日志关联

### 错误日志

```
[ERROR] [code=120002] [traceId=abc] [user=u-001] Metric query timeout
  metric: M-SE-001
  duration: 31s
  killed: true
```

## 十八、错误码治理

- 新增错误码必须在此文档登记
- 文档与代码 `ResultCode` 枚举保持一致（CI 校验）
- 季度评审：废弃不再使用的码
- 错误率统计：每个码的发生频次（Prometheus 指标）
- 高频错误 → 改进产品/技术
