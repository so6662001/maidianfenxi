# 变更管理流程

## 一、为什么需要

中台是多产品共享的基础设施，任何变更都可能影响多个业务方。必须有规范的变更评审与发布流程。

## 二、变更类型分级

| 级别 | 影响 | 评审 | 通知期 |
|---|---|---|---|
| **L1 重大变更** | 影响所有业务方 / 数据口径变化 / 安全策略 | 委员会评审（≥ 3 人） | ≥ 7 天 |
| **L2 影响变更** | 影响多个业务方 / 接口契约变化 / 看板大改 | 跨团队评审（≥ 2 人） | ≥ 3 天 |
| **L3 局部变更** | 影响单业务方 / 内部优化 | 同事评审（≥ 1 人） | ≥ 1 天 |
| **L4 维护变更** | 配置 / 文档 / 性能优化 | Code Review | 无 |

## 三、变更对象与流程

### 1. 架构变更（L1/L2）

```
触发：新增微服务 / 技术栈调整 / 数据流变化
   ↓
提交 RFC（Request For Comments）
   ↓
架构委员会评审（≥ 7 天）
   ↓
通过后更新 docs/02-architecture/
   ↓
分阶段实施
   ↓
归档决策追溯库
```

RFC 模板：
```yaml
RFC ID: ARCH-2026-001
标题: 引入 Apache Pulsar 替代 Kafka
作者: ...
背景: ...
现状问题: ...
方案对比: A / B / C
选定方案: B
影响范围: 所有数据通路服务
风险: ...
回退方案: ...
评审人: ...
状态: draft / under-review / approved / rejected
```

### 2. 指标变更（L1/L2）

```
触发：指标定义口径修改 / 计算公式变化 / 阈值调整
   ↓
数据 PM 提议
   ↓
评估影响（哪些看板 / API / 决策依赖此指标）
   ↓
评审（≥ 2 数据 PM + 1 业务 PM）
   ↓
通知业务方（提前 3-7 天）
   ↓
灰度切换（新口径 vs 旧口径并行 1 周）
   ↓
全量切换
   ↓
旧口径标记 deprecated，6 月后下线
   ↓
归档决策追溯库
```

**关键**：指标变更最容易导致数据信任崩塌，必须强流程。

### 3. Playbook 变更

```
触发：Playbook 效果不达预期 / 业务需求变化
   ↓
Playbook Owner 提议变更
   ↓
评估（历史 ROI / 用户反馈 / 风险）
   ↓
评审（≥ 1 运营 + 1 数据 PM）
   ↓
AB 实验验证（强制）
   ↓
实验显著有效 → 全量
   ↓
实验无效 → 回滚 + 总结
   ↓
归档决策追溯库
```

### 4. API 契约变更

```
分两类：
- 兼容变更（新增字段 / 新增接口）→ L3 流程
- 不兼容变更（字段删除 / 类型变化）→ L1 流程
   ↓
不兼容变更必须：
1. 新版本 v2 上线
2. v1 标记 Deprecation
3. 通知所有业务方（≥ 30 天）
4. v1 至少保留 6 个月
5. v1 下线前 30 天再通知
   ↓
归档变更日志（CHANGELOG）
```

### 5. SDK 变更

```
SemVer 规范：
- 主版本（破坏性）：N → N+1，强制升级
- 次版本（兼容性）：x → x+1，可选升级
- 补丁版本（修复）：x → x+1，建议升级
   ↓
变更流程：
- 主版本：≥ 30 天通知 + 至少 N-2 版本兼容
- 次版本：≥ 7 天通知
- 补丁版本：立即发布
   ↓
CHANGELOG 必须详细
   ↓
迁移指南必须提供
```

### 6. 看板变更

```
小改（字段调整 / 颜色 / 文案）→ L3
大改（重新设计 / 增删模块）→ L2
   ↓
设计稿评审（PM + UX）
   ↓
通知主要使用者（CEO/CFO 等）
   ↓
灰度发布（保留旧版本入口 2 周）
   ↓
全量切换
```

### 7. 嵌入组件变更

```
新增组件 → L3
组件 Props 变化 → L2
组件下线 → L1
   ↓
兼容性测试
   ↓
通知接入方
   ↓
SemVer 发版
   ↓
更新组件库文档
```

### 8. 权限变更

```
触发：新增角色 / 调整权限矩阵
   ↓
评审（安全 + 法务）
   ↓
影响评估（哪些用户权限变化）
   ↓
通知用户（提前 7 天）
   ↓
灰度发布
   ↓
审计变更
```

## 四、变更评审会议

### 月度变更评审会

- 时间：每月最后一周
- 参与：中台 PM 委员会 + 数据 PM + 各产品线代表
- 议题：
  - L1/L2 变更评审
  - 上月变更复盘
  - 本月变更预告

### 紧急评审

- 触发：P0 故障紧急修复 / 安全漏洞
- 流程：≤ 2 小时内召集（电话 / 企微）
- 决策：高级别领导授权
- 事后补完整流程

## 五、变更窗口

### 推荐窗口
- 工作日 10:00-12:00
- 工作日 14:00-17:00

### 禁止窗口
- 周末 / 节假日（除非紧急）
- 大促 / 重要活动期间
- 业务峰值时段
- 月末财务结算期

## 六、变更通知模板

```
【中台变更通知】
变更编号: CHG-2026-0524-001
变更类型: API 契约变更
变更级别: L2

变更内容:
  · POST /openapi/v1/segment/preview 新增字段 sample_users
  · 老字段不受影响

影响范围:
  · 所有调用此接口的业务方

兼容性:
  · 向后兼容（老调用方无需修改）

执行时间:
  · 2026-06-01 14:00

如有问题:
  · 中台 PM：xxx
  · 接入大使群：xxx
```

## 七、变更审计

每次变更必须留痕：
- 变更内容 + 时间
- 变更人 + 审批人
- 影响范围
- 回退方案 + 是否执行
- 评审记录

存储在决策追溯库（应急/常规决策模板）。

## 八、变更失败处理

```
变更失败信号：
- 监控告警飙升
- 业务方投诉
- 数据异常
- 用户反馈
   ↓
立即响应：
- 评估影响
- 决策（继续 / 回滚 / 紧急修复）
   ↓
回滚优先于修复（保护业务）
   ↓
事后复盘（决策追溯库）
- 根因分析（5 Why）
- 改进措施
- 流程改进
```

## 九、变更 KPI

| 指标 | 目标 |
|---|---|
| 变更评审完成率 | 100% |
| 变更通知准时率 | ≥ 95% |
| 变更失败率 | ≤ 5% |
| 变更回滚率 | ≤ 3% |
| 紧急变更比例 | ≤ 10% |
| 变更复盘完成率 | 100% |

## 十、变更工具

- **RFC 仓库**：Git + Markdown
- **评审平台**：决策追溯库 + GitLab MR
- **通知**：企微机器人 + 邮件
- **审计**：决策追溯库
- **看板**：变更月报（Grafana）
