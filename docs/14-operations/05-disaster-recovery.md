# 灾备方案（DR / BCP）

## 一、关键指标

| 指标 | 目标 |
|---|---|
| **RTO**（Recovery Time Objective） | ≤ 30 min（核心服务） |
| **RPO**（Recovery Point Objective） | ≤ 5 min（数据） |
| **MTBF**（平均无故障时间） | ≥ 720 h（30 天） |
| **MTTR**（平均修复时间） | ≤ 60 min |

## 二、灾难等级

| 等级 | 描述 | 响应 |
|---|---|---|
| **L1 单 Pod 故障** | K8s 自动重启 + HPA 扩容 | 自动 |
| **L2 单节点故障** | K8s 自动调度到其他节点 | 自动 |
| **L3 单服务全部故障** | 灰度回滚 / 手动恢复 | < 30 min |
| **L4 单 AZ 故障** | 流量切到其他 AZ | < 30 min |
| **L5 单 Region 故障** | 跨 Region 切换 | < 2 h |
| **L6 数据中心灾难** | 灾备 Region 接管 | < 4 h |

## 三、多 AZ / 多 Region 部署

### MVP 阶段（单 Region 多 AZ）

```
Region: cn-shanghai
├─ AZ-a: 30% 流量
├─ AZ-b: 40% 流量
└─ AZ-c: 30% 流量

每个 AZ 部署完整副本
K8s Service 自动负载均衡
PDB 保证 N-1 可用
```

### V2 阶段（跨 Region 灾备）

```
主 Region: cn-shanghai (active)
   ↓ 数据同步
灾备 Region: cn-shenzhen (standby)

DNS：cloudflare 自动 failover
数据：实时同步（MySQL replica, ClickHouse 双写, Kafka MirrorMaker）
配置：Nacos 跨 Region 集群
```

## 四、数据备份策略

### MySQL

| 类型 | 频率 | 保留 |
|---|---|---|
| 全量备份 | 每日 03:00 | 30 天 |
| 增量备份（binlog） | 实时 | 7 天 |
| 灾备 Region 同步 | 实时（异步复制） | — |
| 长期归档 | 每月 1 号 | 1 年 |

### ClickHouse

| 类型 | 频率 | 保留 |
|---|---|---|
| 副本（同 Region） | 实时 | 副本数 2 |
| 灾备同步（跨 Region） | 实时 | — |
| 快照备份 | 每日 03:00 | 30 天 |
| 冷归档（OSS） | 每月 | 永久 |

### Redis

- AOF + RDB 持久化
- 主从复制
- 数据可丢失（仅缓存），不做跨 Region 同步

### MinIO / OSS

- 跨 Region 复制（每文件）
- 决策快照永久保存

### 配置（Nacos）

- 多 Region 集群
- 每日导出快照到 OSS

### 代码与镜像

- Git 多远程（GitHub + GitLab + 内部 Gitea）
- Harbor 跨 Region 复制
- Helm Charts 多仓库

## 五、备份验证

**每月**：随机选择 1 个备份，恢复到测试环境，验证：
- 数据完整性
- 服务可启动
- 关键查询可执行

**每季度**：完整 DR 演练（详见下文）

## 六、灾备演练

### 月度小演练（30 min）

- 模拟单 Pod 故障 → 验证自动恢复
- 模拟单服务故障 → 验证回滚 SOP
- 模拟单 AZ 流量切换

### 季度大演练（4-8 h）

- 模拟单 Region 故障 → 切换到灾备 Region
- 验证数据一致性
- 验证业务可用性
- 演练后复盘 → 改进措施

### 年度全演练

- 模拟数据中心灾难
- 完整 DR 流程
- 多团队联动

每次演练结果归档到决策追溯库（应急决策模板）。

## 七、跨 Region 切换 SOP

### 触发条件
- 主 Region 完全不可用 ≥ 10 min
- 严重数据故障无法快速恢复
- 高管授权

### 切换流程

```
1. 决策层授权（5 min）
   - L3 oncall 评估
   - 中台负责人 + 高管确认
   
2. DNS 切换（5 min）
   - 域名解析切到灾备 Region
   - Cloudflare 自动或手动切换
   
3. 灾备 Region 激活（10 min）
   - Standby 服务激活
   - 流量验证
   - 监控确认
   
4. 数据一致性验证（10 min）
   - 验证最新数据可读
   - 验证关键业务流程
   
5. 公告通知（5 min）
   - 内部通知
   - 业务方通知（如长时间）
   
6. 持续监控
   - 灾备 Region 稳定性
   - 主 Region 恢复时机
   
7. 主 Region 恢复后切回（24-72h 内）
   - 数据回灌
   - 灰度切流
   - 全量切回
```

### 回切流程

主 Region 恢复后：
1. 数据反向同步（灾备 → 主）
2. 灰度切流（10% → 50% → 100%）
3. 监控 24h 稳定后完成切换
4. 灾备 Region 重新进入 standby

## 八、不同故障场景应对

### 数据库主节点宕机

```
1. 自动 failover（MySQL MHA / 托管自动切换）
2. 应用自动重连从库（升级为主）
3. 旧主修复后作为新从加入
RTO: < 5 min
RPO: < 1 min（binlog 同步延迟）
```

### Kafka 集群故障

```
1. 多 Broker 副本自动选主
2. 单 Broker 故障无感
3. 多 Broker 故障 → Producer 缓冲（本地落盘）+ Consumer 等待
4. 全集群故障 → 切换备用 Kafka 或临时禁用流处理
```

### ClickHouse 节点故障

```
1. 副本自动接管查询
2. 写入临时降级（仅写主副本）
3. 节点修复后 ZooKeeper 自动同步
RTO: < 10 min
RPO: 0（副本同步）
```

### LLM 服务商故障

```
1. 多 Provider 配置自动切换（OpenAI → Claude → 通义千问 → 文心一言）
2. 全部不可用 → 助理降级为只读模式（仅查询，不归因/建议）
3. 用户提示"AI 助理暂时不可用"
RTO: < 1 min（多 Provider 自动切换）
```

### 第三方触达通道故障

```
1. 邮件 SMTP 故障 → 切备用 SMTP
2. 短信故障 → 切备用服务商
3. Push 故障 → 多服务商容错
4. 全部故障 → 任务进入待发队列，30 min 后重试
```

## 九、业务连续性（BCP）

### 核心业务不可中断的能力

| 业务 | 降级方案 |
|---|---|
| 数据采集 | SDK 本地缓存 + 后续重发 |
| 看板查询 | 缓存兜底 + 历史数据展示 |
| 决策助理 | 降级为只读（仅查询，无建议） |
| 嵌入组件 | 降级到只读 + 友好错误 |
| 触达 | 降级延迟（不丢任务） |
| 决策追溯 | 只读优先，紧急时降级 |

### 公关与沟通

- 长时间故障（> 30 min）→ 内部通知
- 长时间故障（> 2h）→ 外部公告
- 严重事件（数据泄露）→ 立即公告 + 法律通报

模板由 PR / 法务团队预先准备。

## 十、灾备成本

- 灾备 Region 资源约为主 Region 的 50%（Standby）
- 全 Region 切换时自动扩容到 100%
- 跨 Region 流量费

## 十一、合规要求

- 数据备份不出境（按《数据安全法》要求）
- 灾备 Region 与主 Region 同一国家
- 备份数据加密存储
- 备份访问审计
